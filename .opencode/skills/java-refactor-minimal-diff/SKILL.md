# java-refactor-minimal-diff

用于在 Java 仓库中做最小改动式重构。

## 适用场景

- 修复代码味道
- 消除重复逻辑
- 调整方法结构
- 修复 warning
- 局部改善可读性、可维护性
- 在不改变外部行为的前提下做内部优化

## 核心原则

- 优先最小改动
- 保持外部行为不变
- 不擅自修改公共 API
- 不做无关大重构
- 不改变既有模块职责边界
- 不顺手改一堆风格无关代码

## 实施步骤

### 1. 明确重构目标

先回答：

- 重构是为了解决什么问题
- 是否有 bug 或 warning 驱动
- 是否需要保持二进制 / 调用兼容
- 是否已有现成模式可复用

### 2. 识别影响面

重点检查：

- public method
- interface
- DTO
- config key
- module dependency
- serialization / deserialization 结构
- 前端或其他模块依赖的响应格式

### 3. 控制改动面

要求：

- 只动必要类和必要方法
- 尽量不改包名、类名、方法名
- 尽量不大面积移动文件
- 避免把“修一个 warning”演化成“全仓风格清洗”

### 4. 保证行为一致

优先通过以下方式证明：

- 现有测试通过
- 新增回归测试
- 关键分支行为保持不变
- 调用链未破坏

### 5. 输出兼容性说明

必须说明：

- 改了什么
- 没改什么
- 为什么这是最小改动
- 是否存在潜在兼容风险

## 适合的重构类型

- 提取私有方法
- 合并重复分支
- 局部命名修正
- 收敛异常处理
- 明确线程边界
- 修复 reactive 链条中的反模式
- 局部拆分长方法

## 不适合的重构类型

- 无任务驱动的全仓大重命名
- 无明确收益的大规模分层重写
- 顺带重写整个配置系统
- 顺带替换框架或底层基础设施

## 输出要求

最终输出应包含：

- 重构目标
- 改动文件
- 保持兼容性的依据
- 验证命令
- 残余风险

## 禁止事项

- 不要改变公共 API 却不说明
- 不要把修复类任务扩大成架构重写
- 不要删除与任务无关但仍有效的旧实现
