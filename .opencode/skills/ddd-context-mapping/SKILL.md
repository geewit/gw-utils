# Skill: DDD Context Mapping

## 适用场景

当任务涉及：
- 梳理限界上下文
- 判断一个功能属于哪个领域
- 识别上下文污染
- 识别 shared kernel / ACL / facade

## 强制规则

1. 先从业务能力和依赖关系切分上下文，不要先按技术层命名上下文。
2. 先回答“谁拥有这条业务规则”，再回答“代码应该放哪里”。
3. 出现以下信号时，优先判断为上下文污染：
   - 同一个对象同时承担 REST DTO、数据库实体、UI 状态、领域规则
   - 其他模块直接依赖本模块内部实现类
   - 某个公共模块持续吸纳私有业务逻辑
4. 若一条规则跨多个上下文，不要立刻合并模型；优先考虑应用服务协作、领域事件或 ACL。
5. 结论必须落到真实包和文件路径，不要停留在概念层。

## 输出模板

- 候选上下文
- 上下文拥有的核心能力
- 依赖的外部上下文
- 污染点
- 推荐收敛 package
- 本轮最小改造点
